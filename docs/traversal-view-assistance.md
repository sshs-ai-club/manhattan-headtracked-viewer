# Experimental traversal view assistance

Issue #21. **OFF by default each session.** Press Esc to open Settings. The separate panel at the upper left enables the experiment and adjusts look-up/down and corner-bank strength independently. Closing Settings resumes movement. Setting either strength to zero removes that cue; switching OFF eases to neutral and restores the original hierarchy. No calibration or preference file is changed.

## Cues and comfort boundaries

- Wall-running ascent above 2 m/s gradually looks up, reaching a target of 55 degrees at 14 m/s (full strength). Minimal-grip wall-anchor ascent uses the same cue when the rope is attached to a vertical surface, the anchor is more than 2 m higher and velocity rises above 2 m/s toward that anchor. This observes the winch ascent without forcing the existing WASD-dependent WallRunning state; roof/ceiling anchors, detached jumps and moving away are excluded.
- Airborne descent above 6 m/s gradually looks down, reaching a target of 35 degrees at 24 m/s. Grounding, ordinary ascent, pause, lost focus and flight mode return toward neutral.
- Horizontal travel above 3 m/s banks into a corner, bounded to 8 degrees at full strength. There is no automatic yaw or route following.
- Default strengths after opt-in are 60% pitch and 35% bank. The targets pass through two cascaded exponential filters: pitch frequency 0.8/s and bank 2/s. Exact sample integration avoids Euler overshoot. For arbitrary bounded target changes, each axis stays inside its target range; pitch rate is below 27 degrees/s and acceleration below 66 degrees/s²; bank below 12 degrees/s and 73 degrees/s². These are autonomous filter bounds, not measured comfort results or combined-axis limits; explicit resets and manual-pole clipping are excluded.
- Applied observer look from any input adapter suppresses assistance targets immediately and holds them neutral for 0.8 seconds after the last change. Existing motion decays smoothly rather than snapping. Manual look still moves immediately and owns the vertical poles. Clipping discards hidden pitch from both filter stages so moving away from a pole cannot reveal stored tilt and cancel the user’s look. This observes the applied view rotation rather than consuming the input source twice.
- Frame gaps above 100 ms discard motion cues and clear heading history; filter time advances by at most 100 ms. Teleports reset cues immediately. Explicit component destruction/disable restores the view immediately; the normal OFF control uses the smooth path.

## Tracking and ownership

The camera and the existing physical screen become children of an identity view pivot below the observer. Only that pivot rotates, before the pinned package's LateUpdate. The package still owns the tracked eye, camera pose and off-axis matrix. Screen-local eye XYZ, calibration, screen dimensions, physical window geometry and projection are unchanged by this rigid transform. Tracking OFF continues to freeze the head offset, not traversal. The feature does not read webcam data as gaze: the current tracker estimates eye position, not gaze direction.

The observer, body, input source, collision/constraint and forces are never changed. The existing camera-based aim ray naturally follows the assisted view, so enabling the view can change what the user chooses to aim at; this is not a claim of identical closed-loop player trajectories. Physics with identical supplied actions remains untouched.

The installer skips benchmarks, scripted/agent traversal and test processes so historical AI route comparisons remain unchanged. No scene, asmdef, package, firmware, v1 wire format or existing input/physics file is edited. Reparenting is refused if another owner has already changed the expected camera/screen hierarchy. Calibration changes while installed are retained on restoration.

## Validation and acceptance

`TraversalViewAssistanceTests` covers wall-running and minimal-grip wall-anchor ascent, fall/landing, opt-out, strength, invalid samples, opposite corners, manual holdoff, reset, stalls, 30/60/144 Hz reversals, frame-rate agreement, vertical poles, screen-space invariance, calibration retention and hierarchy ownership, sub-degree manual look, pole release and the pinned display’s actual LateUpdate/frozen-eye matrix application.

Portable validation: all 172 Python cases completed (147 pass, 25 environment-dependent skips), repository pins/source manifest, Python syntax and whitespace checks pass. The first run failed because the GLB fixture was an LFS pointer; its existing local payload was verified against the manifest SHA-256 and the entire suite rerun. PowerShell is unavailable in this cloud environment.

Native validation of C# revision `be4c4c91`: compilation against actual Unity 6000.3.22f1 assemblies succeeded, and **16/16 camera NUnit cases passed** on the Unity main thread in an isolated Windows Player with the concurrent minimal-grip Core/Viewer assemblies. This used a reflection runner for Test/TestCase, SetUp/TearDown and real NUnit assertions, not the official Unity Editor test runner. It ran without graphics. The actual pinned HeadTrackedDisplay LateUpdate/frozen-eye projection fixture passed; no live webcam observation or rendered-pixel acceptance is implied. Combined traversal-route results are tracked separately under issue #19; camera fixture success is not restricted-route or enabled-component acceptance. The final run includes the wall-anchor ascent regression.

**Clean Unity Editor import/build, rendered Windows UI, live tracking hardware, frame-time measurements, combined human play and comfort are not tested.** The preserved Player’s managed-assembly replacement is not a new full Windows build. Human reviewers must still exercise the normal runtime installer and Settings panel, not only the directly invoked fixtures.

A separate actual-component probe selected AssistanceEnabled and called Update in the real app hierarchy. A further attempt used public KeyboardInput.Capture(true), normal updates for three seconds of fall, and two seconds after OFF. Focus was true, but capture did not remain engaged and motion stayed paused: measured fall peak and OFF angles were zero. The view left the body unchanged. No private capture state or production gate was bypassed. This proves inactive-gate neutrality only, **not active enabled-camera behavior**; an interactive Player/Editor capture test is still required. Baseline AI-route success does not fill this gap because those modes deliberately skip installation.
